# 求职自动化流水线：把「投简历」做成一条可验收的产线

> 这不是一篇讲「怎么用 AI 改简历」的文章。这是一份**工程记录**：一个人用浏览器 CDP + Android adb + 一块 ESP32，把求职这件事拆成规则层、执行层、证据层，然后像跑 CI 一样跑它。
>
> 全文已脱敏：不含姓名、公司名、学校名、HR 联系方式、具体岗位与薪资。
>
> **免责声明**：主流招聘平台的服务条款普遍禁止自动化访问与批量操作。本文是**工程方法论记录**，讲的是「规则表 / 状态机 / 回读验证」这套结构怎么搭，不是「怎么绕过平台风控」。代码片段请只用于你自己有权限的页面、本地测试环境或演示站点；把自动发送降级为「自动整理 + 人工确认发送」是最稳妥的用法。**本文不提供任何「自动打招呼 / 自动发简历 / 批量投递」的实现**，所有写操作一律人工确认后执行；文中代码面向的是你自己有权限的页面与本地测试环境。因照搬导致的账号风险由使用者自负。

## 0. 先给结论

真正卡住求职效率的不是「投得不够多」，而是三件事：

1. **没有判定标准** —— 同一个岗位，今天觉得能投、明天觉得不值得，全靠情绪
2. **没有动作闭环** —— 打招呼、发简历、追进度散在三个动作里，漏一步就断线
3. **没有证据** —— 说「我改好了」，但没人回读确认它真的改好了

所以整条流水线围绕三个词设计：**规则表 / 状态机 / 回读验证**。

---

## 1. 分层结构

```
┌──────────────────────────────────────────────┐
│ L4 证据层   回读验证、体检脚本、截图、日志     │
├──────────────────────────────────────────────┤
│ L3 执行层   浏览器 CDP / Android adb / ESP32  │
├──────────────────────────────────────────────┤
│ L2 状态机   岗位看板：阶段 / 等级 / 备注       │
├──────────────────────────────────────────────┤
│ L1 规则表   阈值、话术、口径、禁区            │
└──────────────────────────────────────────────┘
```

**只写 L3（脚本）是最常见也最没用的做法** —— 脚本跑得动，但你不知道今天该跑多少、什么岗位该发哪版、出问题谁来兜。

---

## 2. 规则层：把判断写成表

规则表要能被机器读、被你复查。我用的是「编号 + 一句可执行判定」的写法，例如（脱敏后）：

| 编号 | 规则 | 判定方式 |
|---|---|---|
| R1 | 薪资门槛 | 达线 → 正常投；卡线 → 先聊；低于底线 → 婉拒 |
| R2 | 经验口径 | 禁止把「总年限」当成「细分年限」说 |
| R3 | 敏感词 | 简历里出现技术黑话 → 判定失败，不发送 |
| R4 | 发送闸门 | 三态判定：已上传 / 待上传 / 未映射，只有第一态允许发简历 |
| R5 | 每日上限 | 自动发送有硬上限，超出即停，不「再投几个」 |
| R6 | 间隔随机 | 条与条之间 ≥90 秒随机，不做匀速 |
| R7 | 异常处置 | 出现验证码/频控/跳登录 → 自己先试 3 次，仍不通才上报 |
| R8 | 联系方式 | 公司正规 + 方向匹配 + 薪资达线 → 才给 |
| R9 | 婉拒清单 | 命中即婉拒不回：园区招商、纯地推、保险财富、培训贷、派遣、电销包装、外地非远程 |
| R10 | 面试时间 | 时间由本人定，助手只给 2–3 个档期，不擅自答应 |
| R11 | 汇报格式 | 固定三段：做了什么 / 证据 / 需要你 |
| R12 | 一岗一版 | 非定制版不发，不同岗位发不同版本 |
| R13 | 定制承接 | 单独计价 + 不占用本岗 KPI 时间 + 结算周期明确，三条同时满足才接 |

**关键设计**：每条规则都要能被 `grep` 到、被脚本引用一次。写在脑子里不叫规则，叫习惯。

## 3. 简历层：版本矩阵，而不是「一版投所有」

我把简历砍到 **3 主投 + 1 备用**，每一版对应一类岗位，配比固定：

| 版本 | 面向方向 | 投放配比 | 页数 |
|---|---|---|---|
| P1 | 实施 / 交付 / 售前 | 40% | 2 页 |
| P2 | 运营 / 生态运营 | 30% | 2 页 |
| P3 | 销售 / 渠道 BD | 20% | 1 页 |
| 备用 | 产品经理 | 0%（遇特别匹配才改抬头） | 1 页 |

为什么按配比而不是按数量？因为**投递配比失配是最常见的隐性错误**：你把 40% 的弹药压在实施岗上，却没有任何一版简历对应实施岗，投一百份也是白投。

工程侧的做法：每版简历是**同一个 HTML 源 + 不同内容块**，PDF 用 headless Chrome 导出，改一处文案 → 重出 → `pdftotext` 回读确认关键字命中。文档永远从源码生成，不手改 PDF。

## 4. 执行层 A：浏览器 CDP

### 4.1 为什么不直接用 Selenium / Playwright

因为要**复用本机会话，避免反复登录**。目标站点的登录态在浏览器 profile 里，重新起一个干净实例等于每次都要重新走一遍登录。做法是：Chrome 以 `--remote-debugging-port` 启动，脚本通过 CDP 连上去。

两个必须知道的前提：

- **Chrome 136 起，默认用户数据目录不再允许开调试端口**。要复用会话，得用独立的 `--user-data-dir` 专用 profile（登录一次，长期复用），不要试图在日用 profile 上开端口
- **调试端口等于把整个浏览器的控制权交给本机任何进程**，包括全部站点 Cookie。只绑 `127.0.0.1`，用完即关，绝不要暴露到局域网或公网

极简 CDP 封装（`cdp.py`，约 130 行，无第三方重量依赖）。**下面这段用于自有测试页 / 本地 demo**，不要拿它去连真实招聘平台的登录 profile：

```python
import json, urllib.request, websocket

PORT = 9222
BASE = 'http://127.0.0.1:%d' % PORT
_ws, _tid, _target = None, 0, None

def pages():
    d = json.load(urllib.request.urlopen(BASE + '/json/list', timeout=10))
    return [x for x in d if x.get('type') == 'page']

def connect(target_id=None, url_contains=None):
    ps = pages()
    t = next(x for x in ps if x['id'] == target_id) if target_id \
        else next(x for x in ps if url_contains in x['url'])
    ...
```

四个原语就够了：`js()` 求值、`nav()` 导航、`click_xy()` 点坐标、`send()` 发原始 CDP 事件。

### 4.2 多标签页是第一个坑

同一个站点常同时开着好几个 tab，其中还有「登录页 / 未登录副本」。连错 tab 的表现是：明明做过的事查不到。

```python
# 正确做法：按 URL 特征挑目标，而不是取第一个
cdp.connect(url_contains='/chat')
```

### 4.3 hover 才出现的按钮：坐标点击会跑偏

真实案例：简历编辑页的「编辑」按钮在 `display:none` 的元素里，鼠标悬停那一行才渲染。用坐标点它的后果是**点到导航栏，整页跳走**，然后你会以为是「登录掉了」。

有效解法有两个，按顺序试（**前提：这是你自己有权限的页面**；对第三方站点的隐藏控件派发事件，请先确认不违反其条款）：

```javascript
// 方案 A：强制显示本身 + 父级
btn.parentElement.style.display = 'inline-block';
btn.style.display = 'inline-block';
// 然后派发合成事件，不依赖坐标
['mousedown','mouseup','click'].forEach(t =>
  btn.dispatchEvent(new MouseEvent(t, {bubbles:true, cancelable:true, view:window, button:0})));
```

```python
# 方案 B：真实鼠标悬停（CSS :hover 才生效的场景）
cdp.send('Input.dispatchMouseEvent', type='mouseMoved', x=r.x, y=r.y, button='none')
time.sleep(0.6)
cdp.send('Input.dispatchMouseEvent', type='mouseMoved', x=r.x+3, y=r.y+2, button='none')
```

**判据**：`getBoundingClientRect()` 返回 `width: 0` ⇒ 元素未渲染或未布局（`display:none` 是其中一种，元素未插入 DOM、在折叠容器里同样返回 0），走方案 A；返回正常尺寸但点击无效 ⇒ 走方案 B。

**方案 A 的边界**：合成事件 `isTrusted` 恒为 `false`，凡是校验 `isTrusted`、或依赖浏览器原生默认行为（label 联动、表单默认提交）的组件，派发事件不会生效。这时只能退回真实鼠标事件（方案 B）。

### 4.4 受控输入框：直接赋值不触发框架

React/Vue 的受控组件，`el.value = 'x'` 只改 DOM 不改状态，提交时会被打回。必须用原生 setter + 事件：

```javascript
const setter = Object.getOwnPropertyDescriptor(HTMLTextAreaElement.prototype, 'value').set;
setter.call(el, newValue);
['input','change','blur'].forEach(ev => el.dispatchEvent(new Event(ev, {bubbles:true})));
```

### 4.5 日期选择器：赋值一定失败，必须点

年月选择器是最顽固的一类。给 input 赋 `2025-03` 后，界面显示是新值，**一提交就被组件内部状态覆盖回旧值**。（下面这套顺序针对的是「懒渲染」型组件库，不是所有日期控件都这样；换成别的库顺序可能不同，判断依据始终是「元素当前有没有被渲染」。）

真实可行的路径（顺序不能乱）：

1. 点开始/结束时间输入框 → 弹出年份列表
2. 点年份单元格（此时月份列表才拿到尺寸）
3. 点月份单元格（「三月」这类中文文本，用 class `.cell.month` 定位）
4. 回读 input 值确认为新值
5. 再点「完成」

第 2 步是最容易漏的：不点年份，月份单元格的 rect 全是 `width: 0`，你会以为它不存在。

## 5. 执行层 B：手机 adb

浏览器解决「网页端」，手机解决「App 端」。手机通道的四件基础设施：

| 能力 | 手段 | 备注 |
|---|---|---|
| 看屏幕 | `adb exec-out screencap -p > s.png` | 比 uiautomator 快，但无结构 |
| 读结构 | `adb shell uiautomator dump` → XML | 拿控件 text / bounds |
| 点与滑 | `adb shell input tap / swipe` | 坐标来自 XML 的 bounds |
| 中文输入 | ADBKeyboard（IME） | 系统 input 只能输 ASCII |

中文输入是必须单独解决的：`adb shell input text 中文` 无效，装一个 ADBKeyboard 后切成该输入法，再用广播把文本送进去。部分国产 ROM 对后台广播、默认输入法切换有额外限制，可能需要手动授权一次。

`uiautomator dump` 的边界：它依赖应用把控件暴露到 accessibility tree。原生控件没问题，WebView 内嵌页面、Flutter/Compose 自绘界面可能拿不到有意义的 `text`，dump 本身也偶发超时 —— 「按文本定位」的前提是文本可访问。

```bash
adb shell ime enable com.android.adbkeyboard/.AdbIME
adb shell ime set com.android.adbkeyboard/.AdbIME
adb shell am broadcast -a ADB_INPUT_TEXT --es msg '你要输入的中文'
```

### 5.1 控制方式怎么选

按「稳定性」从高到低，而不是按「像不像人」：

1. **纯 adb input**：最稳、最快、可复现。缺点是滑动是匀速直线，不适合需要惯性/变速的场景
2. **加随机化**：坐标抖动 ±15px、间隔随机、滑动加中间点。工程目的是**减少误触和避免请求过密触发限流**，不是为了伪装
3. **硬件 HID 外挂**：把开发板当 USB/BLE 键鼠接到手机上，系统看到的是真实 HID 设备。只在「官方接口不可用、adb 被禁用」时才考虑，属于人机交互的备选方案

注意硬件细节：**原版 ESP32 没有原生 USB 外设**，做不了 USB 键鼠，只能走 BLE HID（配对与延迟都是坑）；能直接插上当 USB 键盘的是 ESP32-S2 / S3。而且键鼠 HID ≠ 触摸屏 HID，很多 App 对外接鼠标的点击语义支持并不完整，别指望它完全替代 adb 点击。

我踩过的教训：**不要一上来就搞第三档**。绝大多数任务是「读结构 + 点击 + 等待」，纯 adb 就够；把它包装成幂等动作（先判断当前页，再决定点什么），比提高拟真度更重要。

### 5.2 手机端幂等三件套

```python
def act_on(pattern, action):
    xml = dump_ui()                 # 1. 每次都重新读当前界面
    node = find(xml, pattern)       # 2. 按文本/描述定位，不按固定坐标
    if not node:
        return 'SKIP'               # 3. 找不到就当已达成，不重试到死
    tap(center(node))
    return 'DONE'
```

固定坐标脚本在 2 天内一定失效；按控件文本定位能活很久。

## 6. 闸门与风控：让脚本自己会刹车

### 6.1 发送前先做版本映射（人工确认）

这一节讲的是**校验原则**，不是发送实现。任何一次发送之前，都要先回答一个问题：这个岗位对应哪一版材料？

```
已映射  → 版本正确，可以发
待映射  → 先补映射，暂不发附件
未映射  → 拒发，写日志
```

这一步挡掉的是**最致命的一类错误：把 A 方向的简历发给 B 方向的岗位**。落地方式建议是「脚本把版本候选和岗位标题摆出来，人点确认」，而不是脚本自己点发送。

### 6.2 量的上限与节奏

- 任何自动动作都要有**硬上限**，到量即停，不做「再补几个」
- 动作之间**留足间隔**（不写具体秒数：按你自己的场景定，目的是避免请求过密触发限流，不是「显得像人」）
- 出现验证码 / 频控提示 / 跳登录 ⇒ **立即停止当日全部自动操作，转人工处理，不自动重试**

第 3 条是硬纪律：验证码和频控是平台明确要求「停下来」的信号。正确反应是当天收工、人工接手，而不是换个方式继续试。

### 6.3 材料管理：不常驻、本机留档

附件槽位通常只有 3 个。**不要让材料长期挂在槽位里** —— 它会随时间过期，而你忘了换。

维护原则：按岗位现做 → 用完清理槽位 → 本机保留全量档案与版本对应关系（哪个岗位发的哪一版）。这样任何一次「我到底发过什么」都能查到，靠的是本地台账，不是平台残留。

## 7. 证据层：没有回读就等于没做

这是整篇最想强调的一条。**任何写操作都必须在做完之后回读目标状态**：

| 写操作 | 必须回读的东西 |
|---|---|
| 改了简历某句话 | 重新加载页面后 `body.innerText` 是否命中新文本、旧文本是否消失 |
| 发了消息 | 会话末条是否为该文案 + 状态「送达」+ 输入框已清空 |
| 删了附件 | 附件区是否显示「暂无内容」，条目数是否为 0 |
| 换了日期 | 回读 input 值 + 页面渲染值 |

一个真实场景：**输入框里躺着一条草稿，界面上看着像发出去了**。判断方式是同时查三样：输入框文本长度、会话末条文本、发送态。三者不一致就是没发出去。

再配一个**体检脚本**（十几条断言，跑一遍几秒钟）：项目经历存在、禁忌词为零、期望岗位齐全、附件份数在范围内、状态正确。它的价值在于**每次改动之后你不需要重新怀疑一遍**。

## 8. 状态机：看板而不是待办列表

每个岗位是一条记录，字段固定：

```json
{
  "company": "...",
  "role": "...",
  "stage": "已联系 | 已发简历 | 待面试 | 已面试 | 待结果 | 已拒",
  "grade": "A | B | C",
  "comp_note": "薪资结构/疑点",
  "next_action": "谁在等谁",
  "updated_at": "..."
}
```

`grade` 是决定「要不要主动」的唯一依据：

- **A**：方向匹配 + 薪资达线 + 公司正规 + 有决策人在面 → 24 小时内必回
- **B**：方向偏一点或薪资卡线，但能聊业务 → 正常投，节奏放慢
- **C**：纯销售/纯地推、底薪低于底线、成色不明、面试官不懂业务 → 不主动跟进，等对方

**C 级不是拉黑，是「不投入注意力」。** 每天真正该看的是 A 级那几条。

漏斗脚本按方向 × 回复率、方向 × 面试率出表，每 3 天看一次：哪个方向的回复率明显低，就调配比，而不是加量。

## 9. 真实踩坑清单（按痛感排序）

1. **hover 按钮坐标点击 = 页面跳走**，误判成掉登录。→ 合成事件 + 强制显示
2. **受控输入框直接赋值**，提交被静默打回。→ 原生 setter + input/change
3. **日期选择器不点年份**，月份格子宽 0 点不到。→ 先点年，再点月
4. **多标签页连错**，查什么都查不到。→ 按 URL 特征选 target
5. **草稿没发出去看着像发了**。→ 三处交叉验证
6. **附件长期挂着不换**，简历过期没人知道。→ 用完即删 + 本机留档
7. **固定坐标脚本 2 天必死**。→ 按控件文本定位 + 幂等
8. **只写脚本不写规则**，跑得动但不知道今天该跑多少。→ 规则表前置
9. **投递配比和简历版本不匹配**。→ 用配比表反查版本矩阵
10. **把风控当成可以「再试几次」的东西**。→ 见验证码/频控就当日停手，转人工

## 10. 可以直接抄走的部分

- **一段极简 CDP**（130 行）：连已登录 Chrome，evaluate / 点击 / 输入
- **一套手机幂等动作**：`读 XML → 按文本找 → 点中心 → 找不到就 SKIP`
- **ADBKeyboard 中文输入三条命令**
- **回读验证四件套**：值、渲染、状态、条数
- **只读侧的自动化**：状态巡检、体检断言、漏斗统计 —— 这些不碰平台的写操作，风险最低、收益最直接
- **看板字段模板**与 A/B/C 分级判据

不适合抄的部分：具体的平台选择器、话术文案、行业口径 —— 这些和你的目标岗位绑定，别人给的模板只会让你「看起来像」，不会让你「真的对上」。

---

## 11. 一句话总结

> 求职自动化的产出不是「投了多少份」，而是**一条能自证的状态流**：每条规则可 grep，每个动作可回读，每个岗位有等级和下一步。
>
> 脚本只是把它跑起来。真正的杠杆在规则表和证据层。
